# Decisions

Append-only log of decisions about the software factory. Change a decision by adding a new row that supersedes it; never edit or delete an old row.

| Id | Date | Decision | Why | Source |
|---|---|---|---|---|
| F01 | 2026-10-20 | The factory lives in its own git repo under BSRI (GitHub org `Battlespace-Research`, local `E:\BSRI\GitHub\software-factory`). MACE and NGC2 are read-only references. | The factory is meant for other projects and for sharing, and work on NGC2 continues in other sessions and must not be disturbed. | Owner |
| F02 | 2026-10-20 | The factory runs in Claude Code and in the Codex/ChatGPT app, and one model can drive another. Each role is bound to a vendor, model and effort in one table. | The owner uses both vendors together on NGC2 and expects models to change; swapping a model must be one edit. | Owner |
| F03 | 2026-10-20 | Stages follow the six stages of the Claude Academy AI-native SDLC playbook: Plan, Design, Build, Test, Deploy, Maintain. | Alignment with the playbook is a requirement. | Owner |
| F04 | 2026-10-20 | Users are BSI teammates first, possibly others later. | Sets the bar for documentation and generality. | Owner |
| F05 | 2026-10-20 | Deploy and Maintain treat the desktop installer (today's only deployment) and Kubernetes with Helm (the target) as equal priorities, with separate paths where they differ. Start light and mature from experience, following best practice. | Desktop is what ships now; Kubernetes with Helm is where the work is heading (NGC2 Mission Manager onboarding). | Owner |
| F06 | 2026-10-20 | The factory's diagrams are kept current and published as a private web page (`docs/map/factory-map.html`). | The owner wants to see the framework at every step, including after model or skill changes. | Owner |
| F07 | 2026-10-20 | Each piece of work keeps its state (intent, spec, plan, progress, reviews) as files in the project's own repo, which is the source of truth. GitHub issues are an optional mirror. | Files work the same in Claude Code and Codex, show up in PR review, survive session loss, and match how NGC2 runs. | Owner |
| F08 | 2026-10-20 | Review mode is the default: the factory pauses for the owner's review at its checkpoints. Auto mode is optional and proceeds through checkpoints, stopping only for hard stops. | Teammates new to the factory should see each step; experienced users (as on NGC2) can let it run. | Owner |
| F09 | 2026-10-20 | Reviews run as a panel of parallel reviewers, each with one lens: correctness, security, maintainability, spec compliance (projects may add lenses such as UX or performance). At least one lens is from the other vendor. Any lens's blocker or major sends the task back; maintainability findings alone never block and become follow-up tickets. Fix runs correctness and security; Feature adds maintainability; Program runs all four. | The owner likes the multi-agent review in zazencodes and super-board; the Academy playbook asks for bugs, security and spec-compliance passes. Lens sets per track and the non-blocking maintainability rule are Claude's calls. | Owner + Claude |
| F10 | 2026-10-20 | The factory keeps a dashboard that is updated throughout the work, generated from the project's factory files, git, CI and release records. Template under review: `docs/dashboard/factory-dashboard.html`. | The owner wants to follow progress at a glance; NGC2's dashboard showed the value but is not the template. | Owner |
| F11 | 2026-10-20 | Agent review on GitHub PRs is optional per project and off by default; no GitHub Action for it yet. Deploy stage wording is "merge" (PR if the project uses them). | MACE mostly commits straight to an unprotected main; moving teams to PRs is the owner's call, not the factory's. | Owner |
| F12 | 2026-10-20 | Project setup produces a `REVIEW.md` (lenses, severity scale with a nit cap, per-track lens sets, what to ignore, always-flag project rules) drafted from the repo's existing rules and approved by the owner. The review panel reads it every round; PR review would read the same file. Repeated findings are proposed as additions. | One checklist for every review, aligned with the Academy playbook's REVIEW.md practice. | Owner |
| F13 | 2026-10-20 | Approvals happen in chat. The factory records the owner's exact words, the time, the session and the commit approved in `approvals/`, and never writes an approval without such a message. `factory.yaml` lists who may approve. | Fits how the owner works, often from a phone; a hook can later write the record from the typed message. | Owner |
| F14 | 2026-10-20 | The pilot project is deferred; it will likely be a new MACE plugin. Version 1 is set up and documented first; the README gives a full overview with diagrams. | The owner has enough in flight right now. | Owner |
| F15 | 2026-10-20 | Design rev 2 (`docs/specs/2026-10-20-software-factory-design.md`) is approved, including the calls marked as Claude's. The repo is published as a private GitHub repo, `Battlespace-Research/software-factory`. | Owner, in chat: "Approved, create the repo and push it". Next: the implementation plan. | Owner |
