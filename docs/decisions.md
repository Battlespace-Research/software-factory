| F16 | 2026-10-20 | The factory's names change. The plugin is `bsri-sw-factory` (installed as `bsri-sw-factory@bsri-factory`); its skills are `setup-project`, `intake`, `orchestrate`, `task-loop`, `review-panel` and `merge-gate`, and its subagents `lens-reviewer`, `doc-reviewer`, `tester` and `researcher`; the CLI is `sw-factory`. In a project the factory creates `sw-factory.yaml` and the `sw-factory/` folder, its branches are `sw-factory/<ID>-<slug>` (and `sw-factory/setup`), its section markers `<!-- sw-factory:begin -->` and `<!-- sw-factory:end -->`, and its per-user staging folder is `~/.sw-factory/staging`. Version 0.2.0. Unchanged: the Python package `swfactory`, the `Factory-*` commit trailers, the `FACTORY_*` environment variables, the repo `Battlespace-Research/software-factory`, the marketplace `bsri-factory`, the review-file stamp `<!-- factory: ... -->` and the dashboard's `factory-data` id and `factory-dashboard/0.1` schema. | 'factory' alone is too generic: it could clash on PATH and with projects' own factory/ folders, and the factory's own `triage` skill would sit beside Matt Pocock's `triage`. The plugin prefix already namespaces skills on both hosts, so skill names drop `factory-`. | Owner |
| F17 | 2026-10-21 | The largest track is renamed from Program to **Epic** (track `epic`, ids `EPIC-<n>`, templates `templates/work/epic/`); Fix and Feature are unchanged. Version 0.3.0. | A 'program' usually means a group of related projects, which oversells the track: it is a large feature set with milestones over many sessions — an epic, in the words teams already use in Jira and Azure DevOps (Epic › Feature › bug). | Owner |
| F18 | 2026-10-21 | Three lens reviewers read one of Matt Pocock's skills as a **reference skill**: guidance for their lens, not a procedure to run (no following its steps, no agents spawned, no commands run, no files written because of it; same review format and verdict rules). Correctness reads `tdd` (required): whether the tests really prove the change, behaviour through public interfaces, one behaviour per test, red before green. Maintainability reads `codebase-design` (required): the deep-module vocabulary (shallow modules, leaky seams, interface depth), so findings are concrete. Spec compliance reads `domain-modeling` (optional), only when the project has a `CONTEXT.md` or ADRs: the change uses the project's domain terms and contradicts no recorded decision; the spec lens is given the project's domain files (`CONTEXT.md` anywhere, `CONTEXT-MAP.md`, `docs/adr`, `doc/adr`, `docs/decisions`) and runs that check whenever there are any. Security reads none (Claude Code's `security-review` stays optional). `sw-factory prompt render --reference-skill NAME --host {claude,codex}` **inlines its text** into the lens prompt: the skill's `SKILL.md` plus the files `config/skills.yaml` lists under `read:` (tdd: `tests.md`, `mocking.md`; codebase-design: `DEEPENING.md`, never `DESIGN-IT-TWICE.md`), front matter stripped, at most 32 KB, inside a `<reference-skill>` block with a fixed preface; found in the app's user-level skill folders only, never the project's; `tdd` falls back to `test-driven-development` (`SKILL.md` only); a skill that is not installed gives a fixed sentence. The rendered prompt's `<!-- reference: NAME sha256:<12 hex> -->` line (or `none`) is copied into the review's provenance stamp as `reference=…`, and `claude -p` reviewers run with `--disallowedTools Agent,Skill`. New command `sw-factory skills path NAME --host {claude,codex}` prints an installed skill's `SKILL.md` path, or `none`. The README shows which reviewers run on each track. Version 0.4.0. | The lens checklists were thin; Matt Pocock's skills give the maintainability, correctness and spec lenses a precise shared vocabulary. Reading rather than running keeps one reviewer per lens: code-review would start its own two reviewers. | Owner |
